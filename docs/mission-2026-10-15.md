# Mission for 2026-10-15: first native mero-watch panel

Approved by the owner on 2026-10-14. This records the next work session; it does not schedule an automatic run.

## Goal and success criteria

Demonstrate a visibly distinct native `mero-watch` panel, one custom event handler, and then one live computer value displayed on that panel. A background image, a stored notification, or a renamed but untraced literal does not meet this goal. Firmware installation is already demonstrated; execution and useful behavior of newly added application code remain to be demonstrated.

Retain the working Bluetooth stack and connection behavior, existing controls, basic settings, and updater. Integrate a custom UI mode into the stock firmware before considering a broader replacement. Preserve the original vendor package and its protected recovery copy throughout the work.

## Experiment sequence

1. **Trace one native screen.** Identify its entry path, control tree, layout fields, renderer, and event callbacks using actual firmware and stock resource evidence. Keep tagged-pointer and SDK-version differences explicit. Choose a screen that can be reached reliably and retain a route back to the normal UI.
2. **Build a visibly distinct native panel.** Use verified native elements and a clear `mero-watch` identity. Validate the package offline, preserve unrelated sections, and record hashes and the exact change set before the established Linux update.
3. **Prove custom handler execution.** A local counter or changing diagnostic value must respond to an identified input event. Observe that behavior on the device; a successful OTA result is insufficient.
4. **Display one live machine value.** Extend the custom panel with one agent's name, state, elapsed time, or latest short event. Establish a bounded BLE payload and parsing behavior rather than routing everything through the existing notification inbox.
5. **Add deliberate short commands.** Begin with refresh, last result, and a predefined agent action. Reuse verified controls where practical and check that existing media behavior still works. Avoid treating arbitrary remote shell execution as a prerequisite.
6. **Test phone coexistence separately.** Determine the supported phone/computer connection combinations before designing the iPhone relay. Dual media/data connections do not prove support for two concurrent BLE centrals.

Progress in this order. If the native control or execution path remains uncertain, resolve that specific gap before installing a guessed patch. Keep dated notes with observed, owner-reported, source-correlated, inferred, and untested claims separated.

## mero-shell direction

The first `mero-shell` is a native watch command console backed by the computer: the watch presents short commands, navigation, history, and responses; the computer executes the defined operations. Start with `agents`, agent status, and selected actions. A firmware-local diagnostic console may follow for build identity, connection state, UI events, and other explicitly implemented functions.

No Unix/POSIX shell, process loader, filesystem access policy, or general-purpose terminal inside the current firmware has been established. Those are separate capabilities, not implied by its RTOS or OTA support.

## Application and connection ideas

- **Agents:** list running, waiting, finished, and failed agents; open details.
- **Events:** readable agent and ntfy event history with useful summaries.
- **Commands:** explicit machine actions and their acknowledgements.
- **mero-shell:** selected short commands, history, and scrolling output.
- **System:** build identity, connection state, and basic configuration.

An eventual route may be agent → computer bridge → direct BLE or phone relay → native watch panel. The owner's iPhone and existing ntfy setup are useful targets, but the phone transport, background behavior, and watch/phone/computer coexistence are untested. Initially support one BLE data owner at a time; test mixed phone-media/computer-data arrangements independently. Preserve basic watch settings and connectivity while expanding applications.

## Firmware language and kernel assessment

**Strong inference:** The firmware is predominantly C with low-level assembly, built for Jieli PI32v2/r3. The comparable SDK's C source, C API structure, source-path diagnostics, native symbols, compiled fixture, and exact helper matches support this assessment. We do not possess the full watch source and cannot certify that every component uses the same language. The Linux bridge and analysis tools are Python; that is not the watch firmware language.

**Strong inference:** The kernel is a Jieli port or derivative of uC/OS-II. Five complete reference routine byte sequences match the watch image (`OS_EventTO`, `OS_EventTaskWait`, `OS_InsertListHead`, `OS_RemoveList`, and `os_sem_create`); reference configuration selects `CONFIG_UCOS_ENABLE`. The exact kernel version and vendor modifications are unidentified. See [build analysis](build-analysis.md) and [runtime mapping](native-architecture.md). This evidence supports an embedded RTOS, not an established Linux environment.
